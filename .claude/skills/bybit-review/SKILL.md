# bybit-review — проверять и корректироваться

Цель — не «подкрутить, чтобы стало зелёным», а отличить преимущество стратегии
от везения рынка и менять живую торговлю только тем, что выдержало проверку.
Ответ владельцу — коротко, цифрами, без обещаний прибыли. Торговля бумажная;
реальные деньги, ключи биржи и токены не трогать.

Сервер: `ssh root@192.168.3.5`, проект `/srv/appdata/bybit-bots`, панель
`http://bots.home/`. Код — `E:\development\bybit-bots` (NestJS `server/`, Vue `client/`).

## 1. Факты (2 минуты)

```bash
curl -s http://bots.home/api/health
curl -s http://bots.home/api/stats   # счёт, сделки, лидер авто-выбора
ssh root@192.168.3.5 'cd /srv/appdata/bybit-bots; tail -5 logs/runs.csv; grep -E "^(SYMBOL|INTERVAL|START_BALANCE|FEE_PCT)=" .env'
```

Если `bot` не `running` — сначала чинить работу, разбор потом.

**Актуальность данных** — `feed` в `/api/stats` (и строка «тик …» в логе контейнера):
- `streamConnected: true`, `source: "поток"` — решения по событию закрытия свечи из
  WebSocket Bybit; `lagSec` должен быть ≲ 1–2 с, `fetchMs` — сотни мс;
- `source: "опрос"` при живом потоке или `lagSec` в десятки секунд — поток не работает,
  решения опаздывают до минуты: смотреть лог «поток … оборвался»;
- `staleSkips` > 0 — биржа отдавала устаревшие свечи, тики пропускались: проверить
  сеть сервера и `BYBIT_TIMEOUT_MS`.
Результаты, полученные при опросе или с пропусками, с бэктестом сравнивать осторожно.

## 2. Разложить результат каждого бота

- **Рынок**: лот ~5 $ × изменение цены с момента входа. Цена старта сессии — первая
  строка `logs/equity.csv`. Если минус бота ≈ минус одного лота — это рынок, не стратегия.
- **Издержки**: `fees` в `/api/stats` (USDT × курс). Один круг купил–продал ≈ 0.24 % лота.
  Если издержки ≥ модуля результата — стратегия торгует слишком часто для этого таймфрейма.
- **Стратегия**: остаток после рынка и издержек. Только он говорит о качестве приёма.

## 3. Бэктест — до любых изменений

```bash
cd E:/development/bybit-bots/server
SYMBOL=DOGEUSDT START_BALANCE=11.98 FEE_PCT=0.1 SLIPPAGE_PCT=0.02 \
  npx tsx src/backtest/cli.ts --intervals 5,15,60,240 --days 90
```

Без `--symbols` берёт текущую пару и топ-10 по волатильности. Варианты: как сейчас,
фильтр тренда, стоп-лосс (`--stop 3`), оба. Полные цифры — `builds/backtest-*.json`.
`START_BALANCE` и комиссии — те же, что в `.env` сервера, иначе сравнение неверно.

**Прошла проверку** (`passes`): плюс после издержек и на первых 2/3, и на последней трети
истории, и лучше, чем держать один лот.

Читать с поправкой на множественные сравнения: из ~1600 комбинаций около 5 % проходят
случайно. Доверять только тому, что держится **на нескольких таймфреймах и вариантах
одной пары** или на нескольких парах. Одиночный «+40 %» на одной комбинации — шум.

## 4. Корректировка

Менять живую торговлю, только если есть кандидат, который прошёл шаг 3 устойчиво:

1. Ветка `fix/...`, изменение кода + тест (стратегии — `server/src/trading/strategies/`,
   стоп-лосс — `BotOptions.stopLossPct`, фильтр тренда — `strategies/filters.ts`).
2. `npm run typecheck && npm test` из корня.
3. Смена `SYMBOL`, `INTERVAL`, `START_BALANCE`, комиссий или набора стратегий **сбрасывает
   статистику** — сказать владельцу заранее и спросить. Старую сессию — в архив
   (`scripts/new-session.sh` на сервере), не удалять.
4. Выкладка: `DEPLOY_HOST=root@192.168.3.5 bash scripts/deploy.sh`.
5. Коммиты — по правилам скилла git-commit (по-русски, заголовок ≤ 30 знаков).

Нет устойчивого кандидата — ничего не менять и прямо сказать: преимущества нет.

## 5. Журнал

Каждая проверка — запись в `docs/trading-journal.md`: дата, факты (шаг 1–2), что
показал бэктест, решение и почему, что проверить в следующий раз. Следующая проверка
начинается с чтения журнала: подтвердилось ли прошлое решение на живых данных.

## 6. Ответ владельцу

5–8 строк: что с ботами (цифрами), откуда минус/плюс (рынок / издержки / стратегия),
что показал бэктест, что изменено или предлагается. Без «скоро будет плюс».
